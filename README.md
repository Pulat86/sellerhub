# SellerHub

Платформа управления продажами на маркетплейсах — Uzum Market, Wildberries, Ozon, Yandex Market.

Статус: **Sprint 0**, закладка фундамента.

## Стек

| Слой | Что |
|---|---|
| Фронтенд | React 18 + TypeScript + Vite, TanStack Query, Tailwind, PWA |
| Бэкенд | Supabase: Postgres 17, Auth, Storage, Edge Functions (Deno) |
| Хостинг | Netlify (фронт), Supabase (данные и функции) |
| Языки UI | RU / UZ / EN |

Проект Supabase: `iijjyggbbvrqcbrkjupr`, регион `eu-central-1` (Франкфурт — ближе к Ташкенту и к API маркетплейсов, чем Токио).

## Структура

```
apps/web/              фронтенд
packages/shared/       общие типы, сгенерированные из схемы БД
supabase/migrations/   миграции — единственный способ менять схему
supabase/functions/    Edge Functions
supabase/tests/        тесты БД, в том числе изоляции тенантов
```

## Правила, которые не нарушаются

1. **Схема меняется только миграцией.** Ручные правки в дашборде Supabase не попадают в другие среды и теряются.
2. **RLS включён на каждой таблице.** Фронт ходит в базу напрямую с публичным ключом — таблица без политики читается из консоли браузера целиком.
3. **`tenant_id` в каждой таблице данных продавца.**
4. **Деньги — `numeric`, не `float`.** Время — `timestamptz` в UTC.
5. **`service_role` только в Edge Functions.** В браузер этот ключ не попадает никогда.
6. **Остатки не перезаписываются напрямую** — только через журнал движений.
7. **Строки в UI — только через i18n.**

## Синхронизация

Supabase не даёт долгоживущих воркеров, поэтому работа режется на порции:

```
pg_cron (раз в минуту)
  → app.claim_jobs()   берёт порцию задач (FOR UPDATE SKIP LOCKED)
  → Edge Function      вызывает API маркетплейса на батче 100-500 позиций
  → app.finish_job()   успех или backoff; после max_attempts задача dead
```

Идемпотентность держится на `dedupe_key`: пока задача `pending` или `running`, вторая такая же не создаётся.

Ограничение, о котором надо помнить: при росте до ~100 активных тенантов или ~500k SKU этот слой придётся вынести на отдельный воркер.

## Модель доступа

Роли: `owner`, `admin`, `manager`, `warehouse`, `viewer`.

Источник правды — таблица `memberships`. Политики RLS спрашивают её через `app.is_member()` и `app.has_role()` — это `security definer`-функции с `search_path = ''`. Сами они лежат в схеме `app`, которая не публикуется через PostgREST. Без `security definer` политика на `memberships` вызывала бы сама себя рекурсивно.

Создание компании — только через `public.create_tenant(name, slug)`: она атомарно создаёт тенант и владельца. Прямой `insert` в `tenants` политиками не разрешён.

## Тест изоляции

`supabase/tests/tenant_isolation.sql` — 12 проверок. Проверяет, что пользователь одной компании не видит и не меняет данные другой. Гоняется в CI на каждый PR на чистой базе. Любая строка со значением `ПРОВАЛ` валит сборку.

Новая таблица с данными продавца — новая проверка в этом файле. Это не формальность: пропущенная политика означает, что чужая компания читает твои заказы.

## Вне объёма

По решениям владельца проекта: биллинг и тарифы, POS и офлайн-продажи, витрина интернет-магазина, HR и расчётная ведомость. Платежей в системе нет вообще.
