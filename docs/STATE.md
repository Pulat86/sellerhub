## Как работает очередь — рабочая схема

```
pg_cron (раз в минуту)
  └→ app.dispatch_pending_jobs()      считает pending, читает DISPATCH_URL из app.config
       └→ net.http_post()             асинхронный вызов, fire and forget
            └→ Edge Function dispatch-jobs
                 ├→ public.claim_jobs(10, 'edge-dispatch')    захват порции, SKIP LOCKED
                 ├→ обработчик по job_type                    реестр handlers в index.ts
                 └→ public.finish_job(id, ok, error)          backoff / dead-letter

pg_cron (раз в 5 минут)
  └→ app.reap_stuck_jobs('10 minutes')  освобождает зависшие running-задачи
```

**Конфигурация в базе:** `app.config` — таблица key=value, не публикуется через PostgREST.
Ключ `DISPATCH_URL` = `https://iijjyggbbvrqcbrkjupr.supabase.co/functions/v1/dispatch-jobs`.

**Реестр обработчиков** живёт в `supabase/functions/dispatch-jobs/index.ts`.
Сейчас там один тип — `heartbeat.ping` (диагностика). Адаптеры площадок добавляются туда же в Sprint 1.

## Технический долг, принятый осознанно

- Бандл 528 КБ одним чанком (155 КБ gzip). Резать по маршрутам при росте.
- Разделы Каталог, Заказы, Склад, Аналитика, Настройки — честные заглушки.
- Иконки меню — квадраты-заглушки. Набор выбирается с первым реальным экраном.
- Геометрия внутри `Sidebar` и `States` (3px маркер, 40ch мера) — вне токенов намеренно, не повторяется.
- **Задача `heartbeat.ping` остаётся в базе** как живой индикатор здоровья очереди. Перезапускается вручную сбросом статуса в `pending`.
- **Диспетчер не знает про приоритет тенантов.** Один продавец с большим каталогом может занять всю порцию. Пересматривать при появлении второго активного тенанта.
