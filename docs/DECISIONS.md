# SellerHub — журнал решений

Живой документ. Каждое решение босса фиксируется здесь с датой и последствиями. Документы 00, 01 и 03 подчиняются этому журналу: при расхождении прав журнал.

---

## 29.08.2026

### Р-001. Продукт — только для внутреннего использования. Биллинга нет.
Убираются: тарифные планы, подписки, оплата подписки, страница тарифов, лимиты по тарифу, trial, биллинговые уведомления. Тарифная сетка SellerMind (199k / 499k / 999k сум) остаётся в документе 01 только как ориентир по объёму функций.

**Что остаётся в схеме и почему.** `tenant_id` и RLS — с первого дня. В Supabase фронт ходит в базу напрямую с публичным ключом, и без RLS любой залогиненный пользователь читает всю базу из консоли браузера. Политики пишем в любом случае, `tenant_id` в них стоит ноль. Убрать колонку потом — минута; добавить мультитенантность в готовую систему — переписать каждый запрос и каждую политику.

### Р-002. POS и офлайн-продажи — вне объёма.
Касса, чеки, фискализация, офлайн-режим не проектируются. Источник заказа делаем полем, а не жёстко «маркетплейс» — если POS понадобится, встанет как ещё один источник.

### Р-003. Первая площадка — Uzum Market.
Первый адаптер интеграционного слоя — Uzum, второй — Wildberries. Общий интерфейс адаптеров проектируем сразу под несколько площадок, но до подключения WB считаем его гипотезой, а не проверенным фактом.

**Нужно от босса к старту интеграции:** ключи API продавца Uzum → Supabase Vault, не в чат.

### Р-004. Интернет-магазин / витрина — вне объёма.
Убирается целиком: конструктор витрины, темы, домен, оплата Click и Payme, бонусы, кэшбэк, промокоды, флеш-распродажи, оптовые цены, SEO.

**Следствие:** вместе с Р-001 из проекта уходит любая работа с платежами. Ни подписок, ни приёма оплаты. Деньги считаются по отчётам маркетплейсов.

**Разобрано отдельно 30.08:** экономика витрины — это не продажа модуля, а экономия комиссии на своих продажах Ziyod. Работает только при своём трафике. Решение не пересматриваем, но тему не закрываем: после ядра дешёвый шаг — простая витрина на нашем же каталоге с заказом через Telegram.

### Р-005. HR, KPI и расчётная ведомость — вне объёма.
Убирается: кадровый учёт сотрудников, приказы и контракты с генерацией PDF, расчётная ведомость, KPI-планы, шкала бонусов.

Остаются, потому что это не HR: пользователи системы, роли и права доступа; аудит-лог.

## 30.08.2026

### Р-006. Финансовый учёт — остаётся в объёме.
**Решение босса:** нужен.

Доходы, расходы, кредиторка (AP), отчёты по прибыли. Это учёт бизнеса, а не кадры, и для управления продажами он полезен. Строится после заказов и юнит-экономики — раньше ему нечего считать.

### Р-007. Боковое меню — светлое, а не тёмное.
**Решение босса:** у Billz панель светлая, тёмная утомляет за рабочий день.

Меню переведено на белую панель на светло-сером поле, отделяется границей и отступом. Плата за решение: активный пункт усилен тремя признаками сразу — зелёная подложка, зелёный текст, черта слева, — иначе он теряется в общей светлоте. Токены обновлены в обеих темах.

### Р-008. Акцентный цвет — глубокий сине-зелёный `#0E7C66`.
**Решение босса:** принято.

Выбран так, чтобы не сталкиваться с фирменными цветами площадок: они фиолетовые, розовые и синие и постоянно висят чипами рядом с кнопками. Синий акцент сливался бы с Ozon, фиолетовый — с Uzum, и глаз перестал бы отличать действие от метки площадки.

## 01.09.2026

### Р-009. Функции очереди получают RPC-обёртки в схеме `public`.

**Контекст.** Сквозной прогон диспетчера не работал: Edge Function отвечала `Could not find the function public.claim_jobs`. Причина — Edge Function ходит в базу через PostgREST (`supabase-js .rpc()`), а PostgREST видит только схемы из `api.schemas` — там только `public`. Функции очереди лежат в `app` — намеренно, чтобы браузер их не видел.

**Решение.** Тонкие обёртки `public.claim_jobs`, `public.finish_job`, `public.enqueue_job` — каждая в одну строку вызывает свою версию из `app`. Права выданы только `service_role`; у `anon` и `authenticated` отобраны явно.

**Цена решения.** Функции теперь видны в OpenAPI-схеме PostgREST. Вызвать их без `service_role` нельзя, но сам факт их существования теперь публичен. Это приемлемо: имена функций не секрет, защищает грант, а не неизвестность.

**Альтернатива, которую отклонили:** добавить `app` в `api.schemas`. Это открыло бы браузеру всю служебную схему целиком, включая хелперы RLS-политик.

### Р-010. Диспетчер очереди — проверен сквозным прогоном, архитектура из ADR-001 подтверждена.

Главный технический риск проекта был записан в ADR-001: у Supabase нет долгоживущих воркеров. Предложенная схема — pg_cron дёргает диспетчер, диспетчер через pg_net асинхронно зовёт Edge Function на порцию работы — была гипотезой. Сегодня она проверена на боевом проекте задачей `heartbeat.ping`: `pending` → `succeeded` с первой попытки.

**Точка пересмотра не меняется:** 100 активных тенантов или 500k SKU суммарно — после этого слой выносится на отдельный воркер (Railway/Fly).

### Р-011. Деплой Edge Functions автоматизирован в CI.

Локальной разработки нет, Supabase CLI на машине босса не установлен. Деплой функций вынесен в отдельный джоб `deploy-functions` в `ci.yml`: запускается только при пуше в `main` и только после зелёных миграций и сборки фронта.

Требует секрета `SUPABASE_ACCESS_TOKEN` в GitHub Actions.

**Побочное следствие:** функции едут на прод автоматически при каждом пуше в `main`. Staging-контура для них пока нет. Приемлемо на Sprint 0–1, пересмотреть когда появятся реальные пользователи.

## Итоговый объём

1. **Товары и каталог** — единый каталог, SKU и варианты, изображения, штрихкоды, связка с карточками площадок
2. **Синхронизация** — остатки и заказы, целевой SLA 5–15 минут, журнал синхронизации
3. **Массовые операции** — bulk цены/остатки/статусы, импорт-экспорт Excel, предпросмотр и откат
4. **Ценообразование** — формулы, юнит-экономика, автоакции на неликвид
5. **Склад (WMS)** — приёмка, списание, перемещение, инвентаризация со сканером, журнал движений, резервы
6. **Заказы и аналитика** — единый список, дашборды, сравнение площадок, **финучёт (Р-006)**
7. **Уведомления** — Telegram-бот
8. **Платформенное** — RU/UZ/EN, PWA, роли и права, аудит-лог, шифрование ключей площадок
