# SellerHub — журнал решений

Живой документ. Каждое решение босса фиксируется здесь с датой и последствиями.
Остальные документы подчиняются этому журналу: при расхождении прав журнал.

---

## 29.08.2026

### Р-001. Продукт — только для внутреннего использования. Биллинга нет.

Убираются: тарифные планы, подписки, оплата, страница тарифов, лимиты, trial.

**Что остаётся в схеме и почему.** `tenant_id` и RLS — с первого дня. Фронт ходит в базу напрямую с публичным ключом, и без RLS любой залогиненный пользователь читает всю базу из консоли браузера.

### Р-002. POS и офлайн-продажи — вне объёма.

Источник заказа делаем полем, а не жёстко «маркетплейс» — если POS понадобится, встанет как ещё один источник.

### Р-003. Первая площадка — Uzum Market.

Первый адаптер — Uzum, второй — Wildberries. Общий интерфейс адаптеров проектируем сразу под несколько площадок, но до подключения WB считаем его гипотезой.

**Нужно от босса:** ключи API продавца Uzum → Supabase Vault, не в чат.

### Р-004. Интернет-магазин для покупателей — вне объёма.

Убирается: конструктор витрины, темы, домен, оплата Click и Payme, бонусы, кэшбэк, промокоды, флеш-распродажи, SEO.

**Важное уточнение 01.09.** Слово «витрина» вызвало недоразумение. Р-004 убирает **только магазин для конечных покупателей** — отдельный сайт с корзиной и оплатой. Внутренняя панель продавца со всеми модулями и есть проект целиком, она никогда не урезалась.

### Р-005. HR, приказы и расчётная ведомость — вне объёма.

Убирается: кадровый учёт, приказы и контракты с генерацией PDF, payroll, шкала бонусов.

Остаются: пользователи системы, роли и права доступа, аудит-лог.

**Частично пересмотрено 01.09 — см. Р-012.**

## 30.08.2026

### Р-006. Финансовый учёт — остаётся в объёме.

Доходы, расходы, кредиторка, отчёты по прибыли. Строится после заказов и юнит-экономики — раньше ему нечего считать.

### Р-007. Боковое меню — светлое.

Плата за решение: активный пункт усилен тремя признаками сразу, иначе он теряется в общей светлоте.

### Р-008. Акцентный цвет — `#0E7C66`.

Выбран так, чтобы не сталкиваться с фирменными цветами площадок: синий сливался бы с Ozon, фиолетовый — с Uzum.

## 01.09.2026

### Р-009. Функции очереди получают RPC-обёртки в схеме `public`.

**Контекст.** Edge Function отвечала `Could not find the function public.claim_jobs`. Она ходит в базу через PostgREST, а тот видит только схемы из `api.schemas` — там только `public`. Функции очереди лежат в `app` намеренно, чтобы браузер их не видел.

**Решение.** Тонкие обёртки в `public`, права только `service_role`, у `anon` и `authenticated` отобраны явно.

**Цена.** Функции видны в OpenAPI-схеме. Приемлемо: защищает грант, а не неизвестность.

**Отклонённая альтернатива:** добавить `app` в `api.schemas` — открыло бы браузеру всю служебную схему с хелперами RLS.

### Р-010. Диспетчер очереди проверен, архитектура ADR-001 подтверждена.

Главный технический риск — у Supabase нет долгоживущих воркеров. Схема pg_cron → pg_net → Edge Function была гипотезой, теперь проверена на боевом проекте задачей `heartbeat.ping`.

**Точка пересмотра не меняется:** 100 активных тенантов или 500k SKU.

### Р-011. Деплой Edge Functions и генерация типов — в CI.

Локальной разработки нет, Supabase CLI на машинах команды не стоит. Два джоба: деплой функций и генерация типов с коммитом обратно в репозиторий.

Типы генерируются из локального стека, а не из прода: локальный собран ровно из миграций репозитория.

**Побочное следствие:** функции едут на прод автоматически, staging-контура для них нет. Пересмотреть при появлении реальных пользователей.

### Р-012. KPI-планы возвращаются в объём. Р-005 пересмотрен частично.

**Решение босса:** KPI нужен.

Внутри Р-005 смешались две разные вещи. Кадровый учёт и расчёт зарплат — действительно отдельный продукт. Но план/факт по выручке и марже — это не кадры, а управление продажами. Данные те же самые: заказы, маржа, площадки.

**Возвращается:** KPI-планы по выручке и марже в разрезе площадок и периодов.
**Остаётся вычеркнутым:** payroll, шкала бонусов сотрудникам, кадровый учёт, приказы.

Строится после аналитики — это тот же дашборд с целевым значением рядом с фактическим.

### Р-013. Прогноз закупок — статистика, а не ML на старте.

**Запрос босса:** система рекомендует, сколько какого товара понадобится в следующем месяце, считая за месяц заранее по прошлым продажам.

**Жёсткая зависимость:** прогнозу нужна история продаж. Сейчас заказов ноль. История берётся из API площадок — импорт архива закладывается в адаптер сразу, а не допиливается потом.

**Почему не нейросеть сразу.** На трёх месяцах данных модель переобучится и будет уверенно выдавать неверные числа. Статистика на малых данных точнее и проверяется руками.

**Состав расчёта:** скользящее среднее за 4–8 недель, поправка на тренд, поправка на сезонность при наличии года данных, страховой запас от разброса продаж и срока поставки, вычет текущего остатка и товара в пути.

ML добавляется, когда наберётся год-полтора истории по нескольким сотням SKU.

### Р-014. AI-ассистент по своим данным — только через SQL под RLS пользователя.

**Запрос босса:** панель в аналитике, где можно спросить отчёт, которого нет в шаблонах.

**Модель не считает — модель пишет запрос.** Если спросить у модели выручку за месяц, она ответит правдоподобным числом, иногда неверным. Для системы учёта это недопустимо. Модель получает описание схемы, формулирует SQL, Postgres его выполняет. Все цифры на экране приходят из базы. Сам SQL показывается, чтобы его можно было проверить.

**Запрос исполняется от имени пользователя, под его JWT, с работающим RLS.** Ни в коем случае не под `service_role`: иначе достаточно попросить нужным образом, и ассистент вытащит данные чужого тенанта. Плюс read-only роль, белый список таблиц, запрет всего кроме `select`, таймаут и лимит строк.

**Стоимость.** Каждый вопрос — деньги за токены. Кеш повторяющихся вопросов и лимит закладываются сразу.

Строится после того, как схема аналитики устоится: ассистент без готовых витрин будет писать запросы к пустым таблицам.

### Р-015. Каталог: составные внешние ключи `(id, tenant_id)`.

Обычный ключ по одному `id` позволил бы привязать вариант товара одной компании к товару другой. RLS такую запись не поймает: каждая строка по отдельности законна, нарушение только в связи между ними. Составной ключ делает это невозможным на уровне базы.

В тесте изоляции есть отдельная проверка на этот случай.

### Р-016. Поиск по каталогу — функция в базе с `security invoker`.

Продавец ищет одним полем по названию, артикулу и штрихкоду. Название в `products`, артикул и штрихкод в `product_variants`. Условие «одно ИЛИ другое через связь» PostgREST одним запросом не выражает.

**`security invoker`, а не `definer`.** Функция исполняется от имени вызывающего, значит RLS применяется сам собой. Защищает тот же механизм, что и весь остальной каталог, а не ручная проверка внутри функции, которую можно забыть.

Эта же функция потом послужит сканеру штрихкодов на складе.

## Итоговый объём

1. **Товары и каталог** — единый каталог, SKU и варианты, изображения, штрихкоды, связка с карточками площадок
2. **Синхронизация** — остатки и заказы, целевой SLA 5–15 минут, журнал синхронизации, импорт истории заказов
3. **Массовые операции** — bulk цены/остатки/статусы, импорт-экспорт Excel, предпросмотр и откат
4. **Ценообразование** — формулы, юнит-экономика, автоакции на неликвид
5. **Склад (WMS)** — приёмка, списание, перемещение, инвентаризация со сканером, журнал движений, резервы
6. **Заказы и аналитика** — единый список, дашборды, сравнение площадок, финучёт (Р-006), **KPI план/факт (Р-012)**
7. **Уведомления** — Telegram-бот
8. **Платформенное** — RU/UZ/EN, PWA, роли и права, аудит-лог, шифрование ключей площадок
9. **Прогноз закупок (Р-013)** — после накопления истории продаж
10. **AI-ассистент по данным (Р-014)** — после стабилизации аналитики

## Открытые вопросы

**Справочник контрагентов.** Босс упомянул контрагентов в списке нужного. В утверждённом объёме отдельной строки нет — частично покрывается кредиторкой в финучёте. Предложено решать вместе с WMS: поставщики нужны для приёмки на склад.
